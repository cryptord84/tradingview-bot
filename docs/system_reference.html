1 · System Architecture

Signals originate as TradingView Pine Script alerts and flow through a decision-and-execution pipeline into one of three spot execution venues. A separate module trades Kalshi prediction markets.

Signal pipeline:   Pine alert() (bar close) → HTTPS webhook (JSON payload) → FastAPI receiver → signal log → AI decision layer (risk-scores each signal, may reject or resize) → position sizing (tier % of tradeable balance) → venue router → DEX/CEX swap → position monitor (TP / SL / trailing-stop).

Execution venues (spot, long-only)

  • Solana / Jupiter — DEX aggregator swaps; idle USDC parked in a lending market for yield.
  • EVM / Arbitrum — DEX swaps via an aggregator; idle USDC supplied to a money market.
  • Binance.US — centralized spot for tokens without deep on-chain liquidity.

Core safeguards

  • Price oracle for TP/SL matches the execution route (prevents phantom fills).
  • Every BUY produces a tracked position with TP/SL (fallback ATR if the signal omits one).
  • Illiquid-token size cap (high-slippage memecoins limited to a small fixed %).
  • Bar-close-only firing across the roster (no intra-bar repaint).

Strategy naming: alerts fire on an "Any alert() function call" condition. The webhook payload's strategy string is emitted by the script itself, so the bot resolves sizing tiers and TP/SL profiles from the payload, not the alert's display name.

Gap — the confidence score is a constant. In every script, confidence_score and suggested_position_size_percent are static user inputs, not derived from signal strength — every BUY ships confidence 65 (70 for EMA Ribbon) and size 15%. The bot ignores the suggested size (it applies its own profit-factor tier model) but the AI risk layer still reads confidence_score, so today that input carries no information and never clears the auto-approve threshold. Emitting a computed per-signal confidence (from RSI depth, volume-surge magnitude, or distance past the band/channel) would give the risk layer and sizing something real to act on.

3 · Indicator Reference

All seven are long-only (SELL/short signals were removed in April 2026 to stop cross-strategy interference). Each pairs an edge-triggered BUY with an edge-triggered CLOSE that matches the exit the backtest was validated against.

3.1 · FVG v1.2 — Fair Value Gap  trend / continuation

Concept: trades the ICT "fair value gap" — a 3-candle price imbalance that signals momentum continuation.

  • BUY: a bullish gap forms (low > high[2]), entered on the next bar, confirmed by a volume surge (> 1.5× its 20-bar average).
  • CLOSE: edge-triggered when the gap fills (close < high[2]) or an opposite gap forms — state/signal split so it fires once per fill (this split eliminated ~270 spurious CLOSE webhooks/day from v1.0).
  • Key params: volume MA 20, volume mult 1.5.   Live: NEAR / 1D.

3.2 · EMA Ribbon v1.1  trend

Concept: trend-following on a stacked 3 / 8 / 21 / 55 EMA ribbon.

  • BUY: the first bar the full bullish stack forms (EMA3 > EMA8 > EMA21 > EMA55). No volume or RSI filter on entry.
  • CLOSE: edge-triggered the first bar the stack breaks alignment.
  • Key params: EMA lengths 3/8/21/55; confidence input 70 (the only non-65).   Live: BONK / 4H, SOL / 1D, BTC / 1D.

3.3 · Donchian Breakout v1.1  trend / breakout

Concept: classic Turtle-style breakout of a 20-bar Donchian channel.

  • BUY: close crosses above the prior-bar 20-bar high, with a volume surge (> 1.5× average). Prior-bar channel avoids look-ahead.
  • CLOSE: edge-triggered close under the channel midline.
  • Key params: channel 20, volume mult 1.5.   Live: BTC / 1D, ETH / 1D, DOGE / 1D, RENDER / 4H.

3.4 · Donchian HTF v1.0  trend + regime filter

Concept: the same breakout, gated on a higher-timeframe trend filter (built specifically for the SOL/1D Tier-A passer, where the filter is load-bearing — the unfiltered version fails walk-forward).

  • BUY: Donchian breakout + volume and a 4×-timeframe EMA(20) that is rising (measured on closed HTF bars, no repaint).
  • CLOSE: close under the channel midline (the HTF filter applies to entries only).
  • Key params: channel 20, HTF EMA 20, HTF multiplier ×4.   Live: SOL / 1D.

3.5 · Liquidity Sweep v1.1  reversal

Concept: ICT stop-hunt reversal — a wick that sweeps liquidity below a swing low, then closes back above it.

  • BUY: bar's low pierces the prior swing low but its close is back above it, with a volume surge (> 1.2×, a looser gate than the others).
  • CLOSE: the opposite (bearish) sweep — raw, with no volume gate (v1.0 wrongly gated the exit on volume; v1.1 restored the backtest-matching raw exit).
  • Key params: swing lookback 10, volume mult 1.2.   Live: ATOM / 1D (thin book — depends on limit-order flow).

3.6 · Stochastic RSI v1.1  mean-reversion / oversold

Concept: oversold-reversal momentum — a Stochastic-RSI K/D crossover in the oversold zone with an RSI trend filter.

  • BUY: %K crosses above %D while %K < 20 (oversold) and RSI < 50.
  • CLOSE: %K crosses below %D while %K > 80 (overbought). Entry and exit zones are mutually exclusive, so no same-bar conflict.
  • Key params: RSI 14, Stoch 14, K/D smoothing 3/3, OB/OS 80/20.   Live: FARTCOIN / 4H, OP / 1D, ARB / 1D, ETH / 1D, TIA / 4H, INJ / 1D, LINK / 1D (7 tokens — the widest-deployed indicator).

3.7 · VWAP Deviation v1.2  mean-reversion

Concept: mean reversion off a rolling VWAP with ±σ deviation bands — buys reclaims of the lower band and targets the VWAP.

  • BUY: close crosses back above the lower band (VWAP − 2.5σ) and RSI < 40 (an optional volume filter is off by default).
  • CLOSE: edge-triggered when close crosses back above the VWAP (the reversion target). Emits vwap_target so the bot can cap its take-profit at the mean rather than chasing a breakout.
  • Key params: VWAP period 20, band mult 2.5σ, RSI threshold 40.   Live: FARTCOIN / 4H, MOODENG / 4H, PNUT / 4H, AAVE / 1D, LDO / 1D, ARB / 1D.
Design pattern across the roster: trend strategies (Donchian, EMA Ribbon, FVG) enter on breakout/continuation with a volume gate and exit on structure breaking; mean-reversion strategies (VWAP Dev, Stoch RSI) enter on oversold reclaims and exit at the mean/overbought. Every CLOSE is edge-triggered (one signal per event) — the June 2026 fix that restored these exits is what re-aligned live behavior with the backtests.

5 · Position Sizing Model

Every alert is sized as a percentage of the currently-tradeable balance on its venue. Percentages come from backtested profit-factor (PF) tiers, auto-regenerated nightly and overridable manually.

TierQualifying backtest PFSize (% of tradeable)Typical use
APF ≥ 3.028%Highest-conviction, deepest-sample combos
BPF ≥ 2.020%Strong validated combos
CPF ≥ 1.515%Baseline validated / near-miss watches

Guardrails

  • Illiquid-token cap: a defined list of high-slippage memecoins is capped to a small fixed % regardless of tier — they realized −4% to −7% per trade to slippage before the cap.
  • Hard ceiling: no single position exceeds a fixed maximum % of the venue balance.
  • Minimum trade floor avoids fee-heavy dust trades.
  • Self-throttle: as positions stack, tradeable balance shrinks, so new sizes auto-shrink.

Exit model (bot-side)

  • Trend strategies (Donchian, EMA Ribbon): wider take-profit target.
  • Mean-reversion (VWAP Dev, Stoch RSI): take-profit clamped near the mean; wider stop for oscillation room.
  • Trailing stop with an ATR offset tuned to avoid clipping normal pullbacks.
  • Max-hold cap resolves stragglers that neither TP nor SL catch.
Recent tuning (July 2026): tier sizes were raised (A 18→28, B 13→20, C 9→15) and the venue cash reserve lowered, to let the validated liquid-major combos compound — earlier average trade size was too small to generate meaningful income. Memecoins remain capped.

6 · Kalshi Prediction-Market Side

A separate subsystem trades Kalshi event contracts, isolated from the crypto lanes with its own capital budget and daily loss breaker. Its history is one of repeated strategy failure, and it is currently near-dormant.

Crypto-strikes eligibility gates

A strike must clear all of: model edge ≥ 7¢ · model YES-probability ≤ 0.55 · YES-bid in the 30–55¢ band (so NO costs 45–70¢) · realized-vol within a floor/cap band · time-to-settle between 1.5h and 48h · not already held or session-blacklisted.

Root-cause finding (July 2026): the drought of Kalshi trades is not "no edge" and not a config regression. Eligible strikes keep appearing (1,000+ scans since mid-June), but when the bot places the order, the exchange returns 410 Gone — the strike's order book is empty. These are illiquid out-of-the-money daily strikes (~1–2 days from settling, not near-expiry) that no market-maker quotes; the "edge" is computed off a stale snapshot. The bot correctly blacklists them and moves on. The liquid strikes have no edge; the strikes with edge have no liquidity. Real Kalshi liquidity lives in the 15-minute crypto markets and non-crypto series — a structural dead-end for this product, not a lull.

7 · Gap Analysis & Recommendations

Ordered roughly by expected impact.

HIGH  Kalshi crypto-strikes is a structural dead-end

The daily-strike product cannot fill (empty books; 82 rejected orders in the visible logs). The allocated Kalshi cash has sat idle since mid-June. Recommendation: retire the live crypto-strikes module and redeploy that capital to the only lane with proven, fillable edge (the validated liquid-major crypto combos), or re-point the strategy at a genuinely liquid Kalshi market (15-minute crypto or a non-crypto series) and re-validate before risking capital. A liquidity pre-filter would stop the wasted order attempts but would not by itself create a single fill.

HIGH  Signal cadence is too low to scale income

Only 1D and 4H timeframes are deployed (faster timeframes were dropped for near-zero backtest PF), and the profitable combos are slow (roughly weekly). Realized cadence is only a handful of executions per two weeks. Recommendation: broaden the validated universe (more tokens per strategy) rather than faster timeframes, and concentrate size on the liquid majors that actually carry edge; income is currently constrained by both trade frequency and capital scale.

MED  Indicator utilization is uneven

  • FVG and Liquidity Sweep each run a single token (NEAR, ATOM) — two whole indicators contributing one alert apiece. Either expand them to more validated tokens or accept they are marginal.
  • BTC carries only trend strategies (EMA Ribbon + Donchian) and no mean-reversion; several liquid majors are single-strategy. Diversifying strategy type per token would smooth the equity curve.
  • Mean-reversion clusters on memecoins (which are size-capped for slippage) while trend clusters on majors — the highest-size-allowed names and the highest-signal names don't fully overlap.

MED  Three combos run without backtest validation

BONK/EMA-Ribbon, RENDER/Donchian, and PNUT/VWAP are retained on live results alone (▲ keepers) with no walk-forward pass. They are profitable now but carry decay risk. Recommendation: keep the existing live-vs-backtest comparison discipline and define an explicit cull trigger for each.

MED  Execution-liquidity constraints limit the roster

Several validated combos are undeployable because their token lacks a deep venue: some are blocked by centralized-exchange market-order size caps, others by thin on-chain liquidity (one deployed token trades only a few thousand dollars/day and depends on limit-order flow). Recommendation: add limit-order support on the CEX lane to unlock the size-capped passers, and formalize a minimum-liquidity gate before deploying any new token.

LOW  Long-only; no downside or hedge capture

The system only expresses long views on spot. In sideways or bear regimes it can only sit out. A leverage/short lane was scoped but shelved for tier-stability reasons. Recommendation: revisit a small, gated short/hedge capability once the long side is reliably profitable — not before.

LOW  Monitoring completeness

Delivery monitoring (a webhook-vs-fire heartbeat and reconciliation cron) exists, but end-to-end signal history only goes back to a database rebuild in late May, and the live-vs-backtest profit-factor panel that would close the verdict loop is only partially built. Recommendation: finish the per-combo live-vs-backtest panel so retention/cull decisions are data-driven rather than manual.
